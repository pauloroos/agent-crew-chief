# Plan: ACC 0.8 — SDD, skills kit and a mode without Orca

Status: draft, revised after two Fable 5.1 reviews, 2026-10-31. Base: v0.7.1 (`main` at the 0.7.1 merge).

## Why

0.7.1 slimmed ACC to a coordinator method on Orca plus a model scoreboard
(~750 lines, 4 CLI commands). Three things the owner asked for were lost:

1. **SDD and the interview.** Owner decision on 2026-10-29: keep spec-driven
   work and the interview. 0.7 cut them without asking; the skill now goes
   straight to execution.
2. **The skills kit.** Owner decision on 2026-10-29: the installer copies
   superpowers (test-driven-development, systematic-debugging,
   verification-before-completion) and ponytail (ponytail, ponytail-review),
   and briefs tell workers to use them. 0.7 cut that too.
3. **A mode without Orca.** Not everyone runs Orca; a coordinator in VS Code,
   in a plain terminal or in any CLI must still be able to run lanes.

Constraint from the owner (2026-10-31): stay simple. No return of the 0.6
engine (dispatch, sidecar, slots, maestro, preferences). Everything new is
SKILL.md steps, templates and installer copies; Python only where a test can
prove it.

## Scope

### 1. SDD as the first stage (SKILL.md + 3 templates)

- **When:** any request that is not small. Small = one job, one file area,
  no open question. Small requests skip SDD, and so does any request where
  the user says "run directly" / "sem spec".
- **Interview:** before the spec, the coordinator asks the user the open
  questions in the conversation itself (at most 5, in one message), only
  when the answer changes what gets built. No interview service, no files.
  A user who answers "decide for me" lets the coordinator write its
  assumptions into spec.md and go on to the single stop.
- **Spec:** the coordinator writes `specs/<NNN>-<slug>/spec.md` and
  `tasks.md` (plus `plan.md` only when the design is not obvious) from the
  0.6 templates (restored from git history into
  `skill/crew-chief/templates/spec/`). `tasks.md` marks `[P]` on tasks that
  can run in parallel and "depends on Txxx" for order.
- **One stop:** the coordinator shows the spec summary and the lanes and
  waits for the user's approval. This is the only stop in the whole flow;
  SKILL.md's "do not ask permission between steps" is reworded to name it as
  the one exception.
- **Lanes come from `tasks.md`:** tasks with dependencies or the same files
  share a lane; `[P]` tasks with no shared files go to separate lanes.
- **Spec files are committed on the feature branch before any lane branch
  is created**, so every worker reads them in its own worktree and the PR
  carries them.
- Where to keep specs: `specs/` at the repo root (spec-kit convention) unless
  the project already has a specs folder.

### 2. Skills kit back in the installer

- Restore `vendor/superpowers/` (the 3 skills) and `vendor/ponytail/`
  (ponytail, ponytail-review) from git history (commit 3793c20), with their
  LICENSE and VERSION files.
- `install.py` copies them into `.claude/skills/`, `.agents/skills/` and
  `.gemini/skills/` with the `.installed-by-agent-crew-chief` marker, never
  touching a copy without the marker (0.6 behaviour). Flags `--no-superpowers`
  and `--no-ponytail` come back.
- Same CRLF-safe copy as the skill itself: generalize install.py's
  `_copy_skill` into `_sync_tree(source, destination, marker)` and loop over
  the vendor folders (~30 lines). Do not restore `kit_install.py` or its
  manifest.
- `install_machine_wide.py` copies them too.
- **Job specs** get a fixed "Working rules" block: use test-driven-development
  for code changes, systematic-debugging for bugs, and
  verification-before-completion before `worker_done`; follow ponytail (the
  smallest complete change). A worker without the skills installed reads the
  rule as plain guidance.
- **The coordinator** uses verification-before-completion before it opens
  the PR, and superpowers brainstorming is not required (the SDD stage covers
  it).

### 3. Mode without Orca

- **Choice:** `orca status --json` shows a running Orca → Orca mode (as in
  0.7.1). Otherwise → plain mode. The user can force plain mode by saying so.
- **Plain mode, per lane:**
  1. `git worktree add ../<repo>-acc-<lane> -b acc/<slug>-<lane> acc/<slug>`
     (next to the repo, never inside it).
  2. Write the job spec to a file, `../<repo>-acc-logs/<lane>-<job>.md`, and
     pass the worker a one-line prompt: "Do the job in <absolute path>". A
     spec on the command line breaks on Windows (~8 KB limit, quoting).
  3. Start the worker in the background, from inside the worktree, output to
     `../<repo>-acc-logs/<lane>-<job>.log`, keeping its PID in `<lane>.pid`:
     - Claude Code: `claude -p "<prompt>" --model <model> --dangerously-skip-permissions`
       (refused when running as root, e.g. on a VPS)
     - Codex: `codex exec -C <worktree> -s workspace-write -m <model> "<prompt>"`
     - OpenCode: `opencode run --standalone --auto -m <model> "<prompt>"`
       (`--auto` approves tool calls, else a background run can block
       forever; `--standalone` keeps it in the worktree instead of the
       background service's folder)
     Start and kill, per OS (a short block in SKILL.md, not prose):
     - Linux/macOS: `setsid nohup <cmd> > <log> 2>&1 & echo $! > <lane>.pid`;
       kill with `kill -- -<pid>` (the whole process group, so node children
       die and no ghost executor keeps writing).
     - Windows: `Start-Process -PassThru -RedirectStandardOutput <log>` and
       save `.Id`; kill with `taskkill /PID <pid> /T /F`.
  4. Monitor: process alive, new commits (`git -C <worktree> log`), changed
     files (`git -C <worktree> status --porcelain` and the newest mtime) and
     log growth. Waits stay under 2 minutes per command. `claude -p` prints
     only at the end, so log growth alone is not a progress signal.
  5. **The exit code does not decide the outcome.** The commits and the job's
     check do (claude-ghost exited non-zero after finished runs in 0.6).
  6. Timeout per job: 30 minutes without any commit, file change or log
     growth → kill the process tree and treat it as a failed attempt.
- **Same after that:** review, `ACC record`, merge lanes, PR, cleanup
  (`git worktree remove`, delete lane branches).
- **Optional `ACC run`:** not in 0.8. Revisit only if real runs show the
  coordinator gets the background start or the log wrong.

### 4. Docs, README and a tutorial the owner can validate with

- **README (en + pt-BR):** rewritten around the 0.8 flow: what ACC is (a
  skill plus a scoreboard), the two modes (with Orca / without Orca), SDD, the
  kit, the scoreboard (what each column means, cost tiers, how `pick`
  chooses), install, update, and coming from 0.6. One flow diagram (text).
- **README also gets a "Using it" section** (no separate usage doc):
  example prompts (small fix, feature with SDD, research/review), how to
  force plain mode or skip SDD, how to limit cost (`--max-cost`), how to
  read the scoreboard.
- **Tutorial `docs/tutorial.md` (+ `.pt-BR.md`):** a walk-through the owner
  runs end to end to validate the skill, on an example project that ships
  with ACC (`examples/hello-crew/`, restored and given two independent file
  areas: a `greet` module and a `cli` module, each with its own test, so a
  2-lane request is real):
  1. copy `examples/hello-crew` out of the ACC checkout, `git init`, commit,
     then install ACC into it (inside the ACC repo, lanes and `acc/*`
     branches would land in ACC itself);
  2. paste a fixed request given in the tutorial, written to need SDD and
     to split into 2 `[P]` lanes (one per module);
  3. what the interview, the spec files and the approval stop look like;
  4. what to see while lanes run (Orca panel, or the log files in plain
     mode);
  5. the review, the scores recorded, `ACC score` and `ACC pick`;
  6. delivery: push to a scratch GitHub repo to see the PR, or stop at the
     merged local branch (no remote needed);
  7. a "did it work?" checklist where every item is one command with its
     expected output:
     - `git log --oneline main..acc/<slug>`: the spec commit and 2 lane
       merge commits;
     - `git branch --list "acc/*"`: only `acc/<slug>` after cleanup;
     - `ACC score --kind code`: new rows dated today, one per job;
     - `git ls-remote origin "refs/heads/acc/*"`: no lane branch (workers
       never pushed);
     - `python -m pytest`: green;
     - `ls .claude/skills`: crew-chief, the 3 superpowers skills and the 2
       ponytail skills, each kit folder with its marker.
  Plus a short "small request" run that skips SDD (one lane, no spec files).
- **SKILL.md stays the agent's doc;** human docs live in README/docs only.
- `tests/test_docs.py`: README and tutorial pin the current version, every
  CLI command appears in the README.

- Git rules: feature branch, PR, owner merges; workers never push or merge.

## Test plan

1. `pytest` green.
2. **SDD end to end with Orca:** one small real request in a scratch repo:
   interview → spec files → approval → 2 lanes → workers use the working
   rules → review, record → PR branch merged locally.
3. **Plain mode:** the same request without Orca, one lane with `claude`, one
   with `opencode` (and a `codex` run if quota allows), from a coordinator in
   a plain terminal.
4. Install into a copy of Contratada Fácil: kits land with markers, the
   user's own files are untouched.
5. Run the tutorial exactly as written, both modes, and fix every step that
   does not match what happens.

## Risks and open questions

- **Spec stop vs. "run directly".** The owner wants speed; one approval stop
  is the price of SDD. Small requests skip it.
- **Plain mode monitoring is weaker than Orca's** (no heartbeats, no
  question channel). A worker that needs an answer will stop or guess;
  specs must be self-contained.
- **Codex/OpenCode coordinators untested.** 0.7 was only coordinated from
  Claude Code. In plain mode the Codex sandbox may reap background children
  when its command returns: "Codex coordinator in plain mode" stays marked
  untested until the smoke test proves it.
- **Nested `claude -p`** inside a Claude Code session (CLAUDECODE set) is
  unverified on the current build; the plain-mode smoke test checks it.
- **Specs folder:** a project already on spec-kit has `specs/`; the
  coordinator must look before choosing the folder.
- **Size creep.** Each addition must stay a SKILL step or an installer copy.
